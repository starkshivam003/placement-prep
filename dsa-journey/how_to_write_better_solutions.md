# How to Write Better Solutions

A living log of real mistakes and the concrete fix for each — updated whenever a
new pattern shows up, not rewritten from theory. Add rows, don't delete old ones.

| # | Mistake Pattern | Where It Showed Up | Why It Happens | Concrete Fix |
|---|---|---|---|---|
| 1 | Coding before analyzing constraints | LC3488 Missing Integer (7 failed attempts) — `B[51]` and `sum<51` were guessed from failing tests instead of derived from `nums[i]<=50` | Jumping straight to code skips the step of turning bounds into guaranteed facts | Before writing any code: write down exact bounds (n, value ranges), then write one sentence per bound stating what it *lets you assume*. Only start coding after that. |
| 2 | Bound check placed after array access instead of before/inside loop condition | LC0034, LC0219 (x2) | Loop conditions written by habit, not re-derived per problem | Before finalizing a loop, ask: "is my access guarded by the check, or does the check come too late?" Trace one boundary index by hand. |
| 3 | Signed vs unsigned comparison (`int` vs `size_t`) | Multiple problems using `.size()` | `.size()` returns unsigned; mixing with `int` silently changes comparison semantics | Prefer `int` loop vars cast deliberately, or compile with `-Wall -Wextra` and actually read the warnings, don't ignore them |
| 4 | `==` used where `=` was intended (or vice versa) | reverseKGroup — silent no-op bug | Easy to miss visually, especially under time pressure | Always compile with `-Wall -Wextra`; treat every warning as a real bug until proven otherwise |
| 5 | `static` local variable persisting across calls unintentionally | GCD trial-division infinite loop | `static` state carries between calls in ways that aren't obvious from reading top-to-bottom | Default to non-static; only use `static` with an explicit, stated reason |
| 6 | Introducing a variable to carry a value, then never reading it back | ShiftGrid `temp` bug | Started the right technique, stopped one step short of using it | After writing any temp/helper variable, trace: where is this value actually consumed? |
| 7 | Building a shortcut comparison between two proxies instead of the real final candidates | Maximum Product of Three Numbers (6 attempts) | Assumed a cheaper comparison was equivalent without proving it | Rule: don't build a shortcut comparison unless proven equivalent to comparing the real values — if real values are cheap to compute, just compute them |
| 8 | Explicit state-tracking (flags, search loops) instead of using info pointers already encode | Remove Duplicates II `seen` flag vs `nums[write-2]` | Defaulting to "track more state" instead of asking what's already recoverable | Before adding a new state variable, ask: "is this already recoverable from where my pointers currently are?" |
| 9 | C-style string habits (`'\0'`, `n+1` sizing) applied to `std::string` | Smallest Palindromic Rearrangement I | Abdul Bari's C-style teaching translated directly without adjusting for `std::string`'s self-tracked length | Remember: `std::string` tracks its own length; never manually null-terminate or oversize |
| 10 | Underestimating time, no hard-stop trigger | Multiple 3+ hour sessions estimated at 30 min | No deliberate checkpoint to decide "extend or reroute" | Set a real time-box (25-40 min unaided); when it's hit, consciously choose to extend or step back — don't drift |
| 11 | Reactive bug-hunting instead of proactive reasoning | LC3488 (this session) | Skipping constraint analysis turns debugging into "patch until tests pass" instead of solving | Trace the algorithm by hand on 2 cases (trivial + boundary-stressing) *before* running it — catch bugs by reading, not by the judge |
| 12 | `static` is not inherently dangerous — the real risk is mutating shared state mid-computation across unrelated calls, not persistence itself | LC1137 Tribonacci — first solved via recursion + memoization (worked), then independently realized (Aug 12 morning) that recursion wasn't needed at all: since `n<=37` is fixed and small, the full answer table can be built once and reused forever via a `static` array + a `static bool built` guard — didn't initially know the correct C++ syntax for one-time initialization inside a class body (can't run statements directly in class scope, needs a constructor or a guarded static block) | Distinguish *why* a past `static` bug happened (GCD trial-division: static state got corrupted because it carried partial, call-specific progress across logically independent inputs) from cases where static is actually correct (fixed, input-independent data computed once and read-only forever after, like a full-range lookup table). Rule: ask "is what I'm persisting write-once-then-read-only, or is it being mutated per-call?" — the former is safe, the latter is the GCD-style trap. |
| 13 | Not recognizing a previously-solved technique when it resurfaces in a new problem's surface-different clothing | LC119 Pascal's Triangle II — struggled to find the O(rowIndex)-space in-place solution, even though the exact mechanic (sweep in the direction that lets old values survive long enough to be read before being overwritten) was already used and understood in Minimum Path Sum's space-optimized version | Problems get mentally filed by surface topic (arrays vs DP vs linked lists) instead of by underlying mechanic, so a genuinely repeated technique doesn't get recognized as repeated | Before solving a problem that feels harder than its difficulty rating suggests, ask "what does this problem's *shape* remind me of?" — not the topic, the mechanic (e.g. "update in place without corrupting values I still need," "two pointers converging," "carry propagating in one direction"). Also: an "Easy"-rated problem can still hide a genuinely non-trivial optimal solution — the rating reflects the naive solution's difficulty, not the follow-up's, so struggling on the optimized version isn't a signal about ability. |
| 14 | Assuming an STL mutator function returns the value it removes, without checking its actual signature | `ArrayStack::pop()` using `A.pop_back()` as if it returned a value; later repeated with `queue::pop()` in the two-queue stack attempt | STL naming (`pop`) sounds like it should hand back what it removed, but many STL mutators are `void` — they only remove, they never return; the two responsibilities (read, remove) are separate on purpose | Before calling any unfamiliar STL method, check its actual signature (cppreference) before assuming what it returns. When you need "the value AND its removal," that's almost always two separate calls: read via `.front()`/`.top()`/`.back()`, then a separate `.pop()`/`.pop_back()` with no return used. |
| 15 | Not distinguishing "always cheap" from "amortized cheap" when two valid solutions to the same problem trade off differently | Implement Queue using Stacks — one self-derived solution made `push` always O(n); the reference solution made `push` O(1) and deferred cost to occasional `pop`/`peek` calls | Both solutions satisfy "amortized O(1)," which can look like one must be wrong if they don't behave identically per-call | Amortized O(1) means *total* work across `n` calls is O(n), not that every individual call is fast. Two designs can both be correct and both be amortized O(1) while distributing the cost completely differently (flat tax vs. occasional burst) — check total work across a sequence, not any single call, before judging one "better." |
| 16 | Trying to track a running aggregate (min/max) with a single overwritable variable that can't be "undone" when the element causing it is removed | MinStack — first attempt used one `mini` variable that only ever decreased, with no way to recover the previous minimum after a pop | A single scalar destroys history — once overwritten, the old value is gone, so removal-based undo is structurally impossible | When an aggregate (min, max, sum-so-far) needs to survive pops correctly, store a **parallel stack of frozen snapshots** — one entry per push, each holding "the aggregate as it stood at that exact push." Popping the main stack and popping the snapshot stack together naturally reveals the correct prior state for free, with no recomputation. |


**Meta-rule:** when a new mistake shows up, ask "which existing row is this, or is it genuinely new?" — most bugs are old patterns wearing a new problem's clothes.
